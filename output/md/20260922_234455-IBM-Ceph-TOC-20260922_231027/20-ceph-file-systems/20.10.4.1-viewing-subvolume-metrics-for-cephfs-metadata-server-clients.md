## Viewing subvolume metrics for CephFS metadata server clients

Last Updated
: 2026-09-09

To access subvolume-level metrics, a client can mount a Ceph File System (CephFS) or a specific subvolume.

To access client-specific metrics, a user mounts the complete CephFS. This exposes client-specific metrics of all the operations at the CephFS volume level.

> 📝 **Note:** Note:
When a user mounts an entire CephFS, it leads to performance degradation of the specific file system. To avoid this, users should perform a subvolume level mount.

Using a subvolume level mount has the following benefits:

- It improves the file system performance.
- It enables clients to identify and isolate their operations to specific subvolume paths.

Metrics for throughput, IOPS, latency (read and write), byte consumption, and quota limits are implemented at the subvolume level. These subvolume metrics are collected from all Metadata Servers (MDSs), shared with the metrics aggregator, and aggregated within a sliding window.

### Sliding window

A sliding window is a fixed-size time interval that moves forward incrementally. In CephFS, the sliding window monitors continuous streams of file system activity and performance data. A subvolume is considered active if operations occur within the sliding window. The default window size is 30 seconds.

> 📝 **Note:** Note:
If no activity is detected during this interval, the subvolume is considered inactive.

> 📝 **Note:** Note:
Subvolume metrics are reported only while the subvolume has recent data I/O activity within the sliding window. When a subvolume becomes inactive, metrics are no longer reported until new I/O activity occurs.

The subvolume state (active or inactive) impacts on metrics generation.
Active
The subvolume generates metrics immediately.
Inactive
The subvolume does not generate any metrics and no value is reported.

### Sliding window interval for subvolume metrics

The sliding window algorithm includes the `subv_metrics_window_interval` output value. Both the default and minimum values are defined at 30 seconds.

> 📝 **Note:** Note:

- The sliding window is only available for subvolume metrics, not for client metrics.
- An administrator can configure different default sliding window values for different file systems.

```
name: subv_metrics_window_interval
  type: secs
  level: dev
  desc: subvolume metrics sliding window interval, seconds
  long_desc: interval in seconds to hold values in sliding window for subvolume metrics
  default: 30
  min: 30
  services:
  - mds
```

- Get the `subv_metrics_window_interval` default value by using the ceph config get mds command.

```plaintext-ibm
ceph config get mds subv_metrics_window_interval
```

Copy to clipboard

For example,

```
[root@mon ~]# ceph config get mds subv_metrics_window_interval
30
```
- Change the `subv_metrics_window_interval` default value by using the ceph config set mds command.

```plaintext-ibm
ceph config set mds subv_metrics_window_interval 60
```

Copy to clipboard

For example,

```
[root@mon ~]# ceph config get mds subv_metrics_window_interval
30
[root@mon ~]# ceph config set mds subv_metrics_window_interval 60
[root@mon ~]# ceph config get mds subv_metrics_window_interval
60
```

### Getting subvolume metrics

View aggregated performance and usage metrics for CephFS subvolumes by using the MDS counter dump command.

Before you begin, make sure that you have the following prerequisites in place:

- A CephFS client and MDS version that support subvolume metrics.
- Clients are performing data I/O operations on subvolume paths.
- MDS rank `0` is running and aggregating subvolume metrics.

By default, supported clients negotiate subvolume metric collection with the MDS during session establishment.

If necessary, enable metric collection manually:

```plaintext-ibm
ceph config set client client_collect_and_send_global_metrics true
```

Copy to clipboard

> 📝 **Note:** Note:
If subvolume metrics are not being reported, set
`client_collect_and_send_global_metrics`
to
`true`
and then restart or remount the affected CephFS clients.

To view aggregated subvolume metrics, including the `mds_subvolume_metrics` section, query MDS rank `0` by using the following command:

```plaintext-ibm
ceph tell mds.0 counter dump
```

Copy to clipboard

> 📝 **Note:** Note:
If the
`mds_subvolume_metrics`
section is not present in the output, verify that:

- MDS rank `0` is running and aggregating metrics.
- Clients are performing data I/O operations on subvolume paths.
- The client and MDS versions support subvolume metrics.

CephFS exports gauge subvolume metrics, as defined in Table 1.

| Name | Type | Description |
| --- | --- | --- |
| mds_subvolume_metrics | Array | List of subvolume metric objects . |
| labels | Object | Metadata identifying the file system and subvolume path. |
| fs_name | String | Name of the file system. |
| subvolume_path | String | Path of the subvolume within the file system. |
| counters | Object | Performance metrics for the subvolume. |
| avg_read_iops | Gauge | Average read IOPS (input/output operations per second) over the sliding window. |
| avg_read_tp_Bps | Gauge | Average read throughput in bytes per second. |
| avg_read_lat_msec | Gauge | Average read latency in milliseconds. |
| avg_write_iops | Gauge | Average write IOPS over the sliding window. |
| avg_write_tp_Bps | Gauge | Average write throughput in bytes per second. |
| avg_write_lat_msec | Gauge | Average write latency in milliseconds. |
| quota_bytes | Gauge | The quota limit in bytes configured for the subvolume. A value of 0 indicates no quota is set (unlimited). |
| used_bytes | Gauge | Recursive byte usage of the subvolume root inode. This value is included in mds_subvolume_metrics only while the subvolume has recent data I/O activity within the sliding window. For the authoritative current usage value, use the ceph fs subvolume info command. |

The subvolume metrics are dumped as part of the same command. The `mds_subvolume_metrics` section in the output of the counter dump command displays metrics for each subvolume.

The following is an example with an unlimited quota:

```
"mds_subvolume_metrics": [
    {
        "labels": {
            "fs_name": "cephfs",
            "subvolume_path": "/volumes/_nogroup/test_subvolume"
        },
        "counters": {
            "avg_read_iops": 4,
            "avg_read_tp_Bps": 399,
            "avg_read_lat_msec": 0,
            "avg_write_iops": 2780,
            "avg_write_tp_Bps": 11374658,
            "avg_write_lat_msec": 409,
            "quota_bytes": 0,
            "used_bytes": 2097285
        }
    }
]
```

### MDS rank performance metrics

CephFS exports per-MDS-rank performance metrics as labeled performance counters that can be used to monitor workload and resource usage for each MDS rank.

| Name | Type | Description |
| --- | --- | --- |
| mds_rank_perf | Array | List of MDS rank performance metric objects. |
| labels | Object | Metadata identifying the MDS rank. |
| rank | String | MDS rank identifier. |
| counters | Object | Performance metrics for the MDS rank. |
| cpu_usage | Gauge | CPU usage of the MDS daemon serving the rank, expressed as a percentage. On multi-core systems, this value can exceed 100% because it represents the sum of CPU usage across all CPU cores. |
| open_requests | Gauge | Number of currently open (in-flight) client requests being handled by the MDS rank. |

Because `cpu_usage` and `open_requests` are gauge metrics, the values represent the state of the MDS rank at the time the metrics are collected.

The `mds_rank_perf` metrics are aggregated on MDS rank `0` and include data for all active ranks. Query these metrics from rank `0` by using the ceph tell mds.0 counter dump command.

The `mds_rank_perf` section of the counter dump output displays the metrics for each rank.

For example,

```
"mds_rank_perf": [
    {
        "labels": {
            "rank": "0"
        },
        "counters": {
            "cpu_usage": 145,
            "open_requests": 3
        }
    },
    {
        "labels": {
            "rank": "1"
        },
        "counters": {
            "cpu_usage": 87,
            "open_requests": 0
        }
    }
]
```

> 📝 **Note:** Note:
On multi-core systems,
`cpu_usage`
can exceed 100%. The value represents the total CPU usage aggregated across all CPU cores. For example, a value of
`145`
indicates that the MDS rank is using the equivalent of 1.45 CPU cores.
