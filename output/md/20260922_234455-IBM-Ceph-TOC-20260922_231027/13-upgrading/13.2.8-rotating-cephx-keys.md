## Rotating CephX keys

Last Updated
: 2026-09-09

Rotate CephX client and service-specific keys after upgrade so that all authentication uses the new cipher.

### Before you begin

Before you begin, make sure that you have the following prerequisites in place:

1. Ensure that the Ceph cluster upgrade is complete.
2. Configure the preferred authentication cipher.

> 📝 **Note:** Important:
Set the preferred cipher only when you are certain that no legacy tools or workflows are creating authentication entities that expect older key types.

```plaintext-ibm
ceph mon set auth_preferred_cipher aes256k
```

Copy to clipboard

### About this task

> 📝 **Note:** Important:
`aes256k`
key types are only supported on version
9.9.1.2
or later.

After upgrading Ceph to a version that supports a new cipher, such as `aes256k`, rotate any client CephX keys that are reported as using older cipher types to complete the upgrade.

During upgrade, Ceph automatically rotates service daemon keys for `mon`, `mgr`, `mds`, and `osd`. Client CephX keys are not rotated automatically by `cephadm` and must be rotated manually.

The cluster temporarily supports both the old and new ciphers until all keys are updated.

To understand how CephX key rotation works and when key rotation is required, see CephX key rotation.

### Procedure

1. Identify client keys that still use the old cipher.

```plaintext-ibm
ceph health detail
```

Copy to clipboard

For example,

```
[ERR] AUTH_INSECURE_CLIENT_KEY_TYPE:
entity client.admin using insecure key type: aes
entity client.bootstrap-mds using insecure key type: aes
```

> 📝 **Note:** Note:
Bootstrap keys are often left behind after the initial cluster deployment. These keys are not typically used during normal cluster operation and can be removed if they are no longer required.
2. Rotate the
`client.admin`
key.

Before rotating the `client.admin` key, create and verify a backup administrative credential.

1. Create a backup administrative key.

```plaintext-ibm
ceph auth get-or-create client.admin-backup mon "allow *" | tee ./client.admin-backup.keyring
```

Copy to clipboard
2. Verify that the backup key works.

```plaintext-ibm
ceph -n client.admin-backup -k ./client.admin-backup.keyring auth ls
```

Copy to clipboard
3. Rotate the
`client.admin`
key.

```plaintext-ibm
ceph auth rotate client.admin --key-type aes256k
```

Copy to clipboard
4. Deploy the updated
`client.admin`
keyring.

```plaintext-ibm
ceph auth get client.admin -o /etc/ceph/ceph.client.admin.keyring
```

Copy to clipboard
5. Verify that the updated
`client.admin`
key works.

```plaintext-ibm
ceph auth ls
```

Copy to clipboard
6. Remove the backup administrative key if it is no longer required.

```plaintext-ibm
ceph auth rm client.admin-backup
```

Copy to clipboard

Repeat for each client entity reported by the AUTH_INSECURE_CLIENT_KEY_TYPE health warning.
2. Update the corresponding external or application client keyring.

After rotating an external or application client CephX key, retrieve the updated keyring and distribute it to all nodes and applications that use that client identity.

For example, if you rotate the `client.admin` key, distribute the updated `ceph.client.admin.keyring` file to every node from which Ceph administrative commands are run.

Similarly, when another external or application client identity such as `client.CLIENT_ID` is rotated, distribute the corresponding updated keyring to every node or application that uses that identity.
3. Verify that the updated keyring is being used.
If the updated keyring is not deployed, the node or application continues using the previous CephX key and authentication can fail.
For example,


> 📝 **Note:** Important:
Before disabling the old cipher, rotate all client entities reported by the
AUTH_INSECURE_CLIENT_KEY_TYPE
health warning.

Disable the old cipher only after all reported entities are updated to use the new cipher.

```plaintext-ibm
ceph mon set auth_allowed_ciphers aes256k
```

### Results

All CephX keys use the new cipher, and the cluster accepts only the new cipher.

### What to do next

1. Verify that all keys use the new cipher and that no insecure client keys remain.

```plaintext-ibm
ceph health detail
```

Copy to clipboard

The output does not contain warnings about insecure key types.

The following is an example warning output, if issues remain.

```
[WRN] AUTH_INSECURE_CLIENT_KEY_TYPE:
entity client.storage-user using insecure key type: aes
```

For more information about health check warnings and errors for CephX authentication, see
CephX authentication health checks
.
2. Verify the cluster cipher configuration.

```plaintext-ibm
ceph mon dump | grep cipher
```

Copy to clipboard

The following is an example output:

```
auth_service_cipher aes256k
auth_allowed_ciphers aes256k
auth_preferred_cipher aes256k
```
