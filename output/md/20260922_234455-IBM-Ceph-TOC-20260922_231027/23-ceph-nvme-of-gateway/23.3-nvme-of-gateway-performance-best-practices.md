## NVMe-oF gateway performance best practices

Last Updated
: 2026-09-06

Use the NVMe-oF gateway performance best practices to ensure that you are using the gateway to its fullest capacity.

For high
IOPS
requirements, use a dedicated host for the NVMe-oF gateway.

1. Colocation with OSDs is possible, but the high CPU demand from the gateway might introduce CPU contention especially for write client workloads and when the node has multiple OSDs.
2. For dedicated gateways, the gateway needs a minimum of 16 cores. For higher performance requirements, use 30 or more cores.

### Deployment best practices

The NVMe-oF gateway service automatically stores the service configuration in a pool called `.nvmeof`.

> 📝 **Note:** Note:
Deploying multiple NVMe-oF gateway groups on different Ceph Block Device-enabled pools (RBD application-enabled pools) is supported but not recommended.

Ceph NVMe-oF gateway uses Linux huge pages by default to improve memory performance. To configure the Ceph NVMe-oF gateway to run without huge pages, see Configuring the gateway to run without huge pages.

### Rule of Thumb (RoT) sizing guide

The following
RoT sizing
is based on the mixed workload scenario at latencies less than or equal to 10 ms, with an environment based on 100 Gb networking, with 72 namespaces.

| IOPS goal | Number of reactor cores | Total CPU demand (cores) | tgt_cmd_extra_rags specification parameter |
| --- | --- | --- | --- |
| Up to 100,000 | 1 | 16 | --cpumask=0x1 |
| Up to 200,000 | 2 | 18 | --cpumask=0x3 |
| Up to 250,000 | 4 | 22 | --cpumask=0xF (default) |
| Up to 300,000 | 8 | 30 | --cpumask=0xFF |

`FF`
is a hexadecimal bit mask that is based on the number of cores that are used in the cluster.
In the following example, 8 cores are used, so the value of
`--cpumask`
is
`0xFF`
. For 6 cores, the value is
`0x3F`
.

```
[ceph: root@host01/ ]# cat file.yaml
service_type: nvmeof
service_id: nvmeof.group1
placement:
  hosts:
    - host01
    - host02
spec:
  pool: .nvmeof
  tgt_cmd_extra_args: --cpumask=0xFF
```

### VMware ESX recommendations

1. Allocate more of the smaller datastores instead of a few large datastores. This approach does not carry capacity cost as Ceph has thin provisions by default and helps ensure that Ceph I/O contexts are available for the gateway.
2. Consider isolating applications with high I/O demands to use a dedicated datastore to ensure adequate host adapter queue depth.
3. Use jumbo frames when possible for ESXi to Gateway network links. Using jumbo frames is beneficial for workloads that use larger I/O block sizes.
