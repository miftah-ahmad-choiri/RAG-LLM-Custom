## Certificate management

Last Updated
: 2026-09-06

Manage TLS certificates for IBM Storage Ceph services with the cephadm certificate manager (certmgr). Supports self‑signed and bring‑your‑own certificates.

certmgr acts as the Root Certificate Authority (CA) for all self-signed certificates generated by cephadm. For services that require SSL, administrators can either bring their own certificate or allow cephadm to generate a self-signed certificate. This ensures secure communication while offering flexibility for deployment preferences.

certmgr automatically detects whether a certificate is self-signed (generated by cephadm), user-provided as an embedded value in the service specification, or referenced externally. This distinction determines how expiration and renewal are handled.

Self-signed certificates
With self-signed certificates:

- certmgr fully automates renewal, helping to ensure seamless service operation.
- Automation is controlled by configuration parameters that define certificate duration, renewal thresholds, and whether automated rotation is enabled.

User-provided certificates
There are two types of user-provided certificates: inline and reference.
Inline certificates
Certificates are embedded in the service specification. These certificates cannot be modified directly with
certmgr
.
Reference certificates
Certificates are set and managed with
certmgr
. These certificates must be uploaded manually.

For more information about how certmgr handles user-provided certificate expiration, see Certificate health monitoring.

### Lifecycle configuration

To manage certificate lifecycles, certmgr continuously monitors certificates and applies renewal policies based on the certificate type and configured parameters. cephadm provides several configuration options to manage certificate lifecycle and renewal.

Table 1 details the available configuration options, values, and descriptions.

| Configuration | Values | Description |
| --- | --- | --- |
| mgr/cephadm/certificate_automated_rotation_enabled | Default true Additional values false | Enabled by default, this configuration option controls whether cephadm automatically rotates certificates upon expiration. When disabled, cephadm still checks certificates periodically, but instead of automatically renewing self-signed expired certificates, it issues a health error or warning when an issue is detected. |
| mgr/cephadm/certificate_duration_days | Default 3 * 365 Minimum 90 Maximum 10 * 365 | Specifies the duration (in days) of self-signed certificates generated and signed by the cephadm root CA. |
| mgr/cephadm/certificate_renewal_threshold_days | Default 30 Minimum 10 Maximum 90 | Defines the number of days before certificate expiration when cephadm initiates renewal. This applies to both self-signed and user-provided certificates. For user-provided certificates, cephadm issues a health error or warning alerting administrators to the upcoming expiration. |
| mgr/cephadm/certificate_check_period | Default 1 Minimum 0 Maximum 30 | Specifies how often (in days) certificates are checked for validity. Setting this parameter to 0 disables certificate checking. |

### Certificate health monitoring

cephadm continuously monitors the status of all managed certificates, both self-signed and user-provided.

- If a certificate is invalid or expired, cephadm issues a health error (CEPHADM_CERT_ERROR).
- If a certificate is approaching its expiration date, as determined by mgr/cephadm/certificate_renewal_threshold_days, cephadm issues a health warning.

Self-signed certificates are automatically renewed by cephadm when automated rotation is enabled, but user-provided certificates must be updated manually.

### SSL fields in service specifications

Service specifications that support SSL/TLS can define specific configuration fields. Table 2 defines the optional configuration fields and their values.

> 📝 **Note:** Note:
If you set
ssl
to
`true`
without additional configuration, the certificate manager issues
cephadm
‑signed certificates for the service by default.

| Field | Values |
| --- | --- |
| ssl | Boolean to enable or disable SSL (true or false) |
| ssl_cert | Use for inline: certificate content |
| ssl_key | Use for inline: key content |
| certificate_source | One of the following: inline reference cephadm_signed |

> 📝 **Note:** Note:
If
certificate_source
is set to
`reference`
and the certificate is missing, you must upload both the certificate and the key. Use the names shown in the output of the
ceph orch certmgr bindings ls
command:

```plaintext-ibm
ceph orch certmgr cert set --cert-name CERT_NAME --service-name SERVICE_NAME -i CERT_FILE
ceph orch certmgr key set --key-name KEY_NAME --service-name SERVICE_NAME -i KEY_FILE
```

### Certificate scopes

certmgr supports three scopes for certificate management: global, per-host, and per-service.

| Scope | Description | Example services |
| --- | --- | --- |
| Global | Certificates in this scope are shared across all service daemons regardless of the host on which they run. | mgmt-gateway certificate is a globally shared certificate used by all service daemons. |
| Per-host | Certificates are assigned per host, meaning each host has its own unique certificate. When configuring a custom certificate, specify the target host. | grafana service certificates are configured at the host level and apply specifically to a single machine. For step-by-step instructions, see Configuring a Grafana certificate. |
| Per-service | Certificates are configured per service name, where each service instance can have its own certificate. When specifying a custom certificate, define the target service name. | A Ceph Object Gateway (rgw) service certificate is assigned specifically to a Ceph Object Gateway service. |
