### CephHealthError

**Severity:** Critical

This alert is triggered when the cluster remains in the HEALTH_ERROR state for more than 5 minutes. This condition indicates a serious issue that affects cluster stability or data availability.

To resolve the issue, complete the following steps:

1. Check the cluster health:

```plaintext-ibm
ceph -s
```

Copy to clipboard
2. Review the detailed errors:

```plaintext-ibm
ceph health detail
```

Copy to clipboard
3. Resolve the reported issues.
4. Verify that the cluster returns to a healthy state.

### CephHealthWarning

**Severity:** Critical

This alert is triggered when the cluster remains in the HEALTH_WARN state for more than 15 minutes. This condition indicates degraded performance or potential risks that require attention but are not yet critical.

To resolve the issue, complete the following steps:

1. Review the detailed health warning.
2. Resolve the reported issues.
3. Verify the cluster returns to healthy.

### CephMonDownQuorumAtRisk

**Severity:** Critical

This alert is triggered when the monitor quorum is at risk. Quorum requires a majority of monitors (for example, 3 of 5) to be active. Without quorum, the cluster becomes inoperable and all services and clients are affected.

Perform the resolution steps on the node where the monitor daemon is down.

To resolve the issue, complete the following steps:

1. Identify the node where the monitor daemon is down:

```plaintext-ibm
ceph status
ceph orch ps | grep mon
```

Copy to clipboard

          The `ceph orch ps` output shows the host and daemon name for each monitor, which you use to locate the affected node.
2. On the affected node, check the current status of the monitor service:

```plaintext-ibm
systemctl status <mon-service-name>
```

Copy to clipboard
3. Verify whether the service is active or failed. If the service is not running, start it on the affected node:

```plaintext-ibm
systemctl start <mon-service-name>
```

Copy to clipboard
4. Recheck the service status to confirm that it is running.
5. If the service fails to start, check the logs and determine whether the monitor database is corrupted.
6. If corruption is detected, replace the monitor. For more information, see Ceph Monitor is out of quorum.

### CephMonDiskspaceCritical

**Severity:** Critical

This alert is triggered when the available free space in the Ceph monitor store is critically low. If the disk becomes full, the monitor service might stop functioning, which can affect quorum and overall cluster stability.

The default store locations are:

- From the cephadm shell: /var/lib/ceph/mon/ceph-<mon-name>/store.db
- From the host:
/var/lib/ceph/<fsid>/mon.<daemon-name>/

> 📝 **Note:** Note:
Do not stop multiple monitor daemons simultaneously. Always ensure that quorum is maintained while you perform maintenance.

To resolve the issue, complete the following steps:

1. Ensure that the cluster is healthy and that monitors are in quorum:

```plaintext-ibm
ceph -s
```

Copy to clipboard
2. Check the overall disk space on the monitor nodes:

```plaintext-ibm
df -h
```

Copy to clipboard
3. Identify disk consumption from logs and of the monitor data:

```plaintext-ibm
du -sh /var/lib/ceph/mon/*
```

Copy to clipboard

> 📝 **Note:** Note:
In many deployments, the log directory (
`/var/log/ceph/`
) is mounted on a separate disk or volume. Its usage does not necessarily reflect the available space in the monitor store, so it is not included in this check. Log cleanup is covered in a later step.
4. Locate the correct monitor database path:

- Standard location: `/var/lib/ceph/mon/ceph-<mon-name>/store.db`
- cephadm deployments (host view): `/var/lib/ceph/<fsid>/mon.<daemon-name>/`

> 📝 **Note:** Note:
Inside the cephadm shell, paths appear differently.

  - Standard location: `/var/lib/ceph/mon/ceph-<mon-name>/store.db`
  - cephadm deployments (host view): `/var/lib/ceph/<fsid>/mon.<daemon-name>/`
5. Free up disk space safely:

- Rotate or clean old log files under `/var/log/ceph/`.
- Remove unnecessary temporary or debug files.
- Ensure that sufficient free space is restored.

> 📝 **Note:** Important:
Do not delete or modify monitor database files (
`store.db`
), because doing so can cause monitor failure or data loss.

  - Rotate or clean old log files under `/var/log/ceph/`.
  - Remove unnecessary temporary or debug files.
  - Ensure that sufficient free space is restored.
6. Investigate whether excessive monitor database growth is caused by frequent cluster map updates (for example, flapping OSDs), and address the root cause.
7. Expand storage if required. Increase the disk capacity of the monitor nodes.
8. Maintain quorum during operations.
9. Verify recovery and confirm that the alert is cleared and that monitors are stable:

```plaintext-ibm
ceph -s
```

Copy to clipboard

### CephOSDDownHigh

**Severity:** Critical

This alert is triggered when a significant number of OSDs are down, which can affect data redundancy and cluster performance.

To resolve the issue, complete the following steps:

1. Verify the overall cluster health and identify the down OSDs:

```plaintext-ibm
ceph -s
ceph osd stat
ceph osd tree
```

Copy to clipboard

> 📝 **Note:** Note:
The
`ceph osd tree`
command is sufficient to identify down OSDs.
2. Identify whether an OSD went down because of a crash:

```plaintext-ibm
ceph crash ls
ceph crash info <crash-id>
```

Copy to clipboard

          This information helps determine whether the issue is related to a bug or a recurring failure.
3. Restart the failed OSD by using the correct systemd unit format (with the FSID):

```plaintext-ibm
systemctl restart ceph-<fsid>@osd.<osd-id>.service
```

Copy to clipboard

          For example:

```plaintext-ibm
systemctl restart ceph-861a07b2-1179-11f1-bb0e-52540048746d@osd.0.service
```

Copy to clipboard
4. Check the logs for disk, host, or network-related problems:

```plaintext-ibm
journalctl -u ceph-<fsid>@osd.<osd-id>.service --no-pager
```

Copy to clipboard
5. Address the root cause:

- Fix hardware issues (disk, node, or network).
- Investigate frequent failures or flapping OSDs.
- Resolve bugs if crashes are observed.

  - Fix hardware issues (disk, node, or network).
  - Investigate frequent failures or flapping OSDs.
  - Resolve bugs if crashes are observed.
6. Replace or recreate the OSD if required:

- Replace the failed disk if necessary.
- Recreate the OSD by using `ceph cephadm` only (not `ceph-volume` manually).
- Follow the appropriate procedure based on the deployment type (colocated, non-colocated, or custom LVM).

          For more information, see Replacing an OSD drive.

  - Replace the failed disk if necessary.
  - Recreate the OSD by using `ceph cephadm` only (not `ceph-volume` manually).
  - Follow the appropriate procedure based on the deployment type (colocated, non-colocated, or custom LVM).
7. Verify cluster recovery:

```plaintext-ibm
ceph -s
```

### CephOSDFull

**Severity:** Critical

This alert is triggered when one or more OSDs reach the FULL threshold. When this occurs, writes to pools that use the affected OSDs are blocked. This condition can halt client I/O and place the cluster at risk until it is resolved. For more information about resolving OSD full issues, see Troubleshooting Ceph OSDs.

### CephDeviceFailurePredictionTooHigh

**Severity:** Critical

This alert is triggered when the device health module predicts multiple device failures, but remediation cannot proceed automatically. Removing too many OSDs at once risks cluster performance and availability. To prevent data integrity issues, add new OSDs so that data can be relocated safely.

To resolve the issue, complete the following steps:

1. Check device health:

```plaintext-ibm
ceph device ls
ceph device info <device-id>
```

Copy to clipboard
2. Review the SMART metrics:

```plaintext-ibm
smartctl -a /dev/<device>
```

Copy to clipboard
3. Mark the corresponding OSD out. Monitor the cluster status and ensure that all placement groups (PGs) return to a healthy state:

```plaintext-ibm
ceph -s
```

Copy to clipboard

> 📝 **Note:** Note:
Proceed only when the PGs are active and clean.
4. After the data is rebalanced safely, remove the OSD from the cluster:

```plaintext-ibm
ceph osd purge <osd-id> --yes-i-really-mean-it
```

Copy to clipboard
5. Physically replace the disk and recreate the OSD by using the appropriate deployment method.
6. Verify cluster health:

```plaintext-ibm
ceph -s
```

Copy to clipboard

### CephFilesystemDamaged

**Severity:** Critical

This alert is triggered when CephFS metadata becomes corrupted, which might render data inaccessible. Analyze the metrics from the MDS daemon admin socket, or escalate the issue to support for recovery actions.

To resolve the issue, complete the following steps:

1. Check the cluster health:

```plaintext-ibm
ceph -s
```

Copy to clipboard
2. Check for for a message similar to the following:

```
MDSs report damaged metadata
```
3. Check the filesystem status:

```plaintext-ibm
ceph fs status
```

Copy to clipboard
4. Inspect the MDS status:

```plaintext-ibm
ceph mds stat
```

Copy to clipboard
5. List the reported metadata damage:

```plaintext-ibm
ceph tell mds.<fs-name>:0 damage ls
```

Copy to clipboard

Review the reported damage type. If the damage type is <b>backtrace</b>, follow the documented recovery procedure for metadata damage. Different damage types require different recovery procedures.If the reported damage type is not recognized or recovery is unsuccessful, contact IBM Support for further assistance. Avoid attempting manual metadata repair without guidance, because incorrect recovery actions can result in data loss.

### CephFilesystemOffline

**Severity:** Critical

This alert is triggered when all Metadata Server (MDS) ranks are unavailable. With no active MDS daemons, the CephFS filesystem cannot serve metadata requests and becomes offline.

To resolve the issue, complete the following steps:

1. Check the MDS status:

```plaintext-ibm

```

Copy to clipboard
2. Restart the MDS daemons.
3. Ensure that sufficient active MDS daemons are available.
4. Verify that the filesystem comes online.
