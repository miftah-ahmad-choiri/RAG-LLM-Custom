## Managing NVMe‑oF stretch cluster behavior

Last Updated
: 2026-06-25

Managing NVMe-oF stretch cluster behavior by controlling failover, failback, and namespace placement across gateway locations.

### Before you begin

Before you begin, make sure that you have the following prerequisites in place:

- A configured NVMe-oF stretch cluster with gateways assigned to locations.
- Existing NVMe-oF subsystems and namespaces assigned to locations.

### About this task

After configuration, NVMe-oF stretch cluster deployments can be adjusted by controlling gateway location state and namespace placement. These operations affect failover behavior, failback control, and load balancing between sites.

### Managing NVMe-oF site in disaster state

Control failover and failback behavior in an NVMe-oF stretch cluster by marking a gateway location as in a `disaster` state.

#### About this task

When a site is in a disaster or degraded state, it is recommended to mark the gateways in that location as in a
`disaster`
state.

Setting the gateways in a `disaster` state allows administrators to control failback timing during recovery. Without setting the `disaster` state, the NVMe-oF control plane automatically fails back traffic to a site as soon as it becomes reachable.

In some scenarios, automatic failback is not desired. For example, failback can be delayed until the underlying storage layers, such as OSDs, are fully verified and stable.

> 📝 **Note:** Note:
When a location is set to a
`disaster`
state, failback to that location does not occur until the disaster state is cleared.

#### Procedure

Set the
`disaster`
state for a location.

```plaintext-ibm
ceph nvme-gw disaster-set POOL_NAME GROUP_NAME LOCATION
```

Copy to clipboard

The following example prevents failover back to the DC3 location during recovery:

```
[root@host01 ~]# ceph nvme-gw disaster-set pool01 group01 DC3
```

The specified location is excluded from failover selection and automatic failback to that location is blocked.

### Managing failback behavior

Restore a location in an NVMe-oF stretch cluster by clearing its `disaster` state and enabling failback.

#### About this task

Clearing the
`disaster`
state allows the location to participate in failover selection and triggers a failback, if needed.

#### Procedure

Clear the
`disaster`
state for a location.

```plaintext-ibm
ceph nvme-gw disaster-clear POOL_NAME GROUP_NAME LOCATION
```

Copy to clipboard

For example,

```plaintext-ibm
[root@host01 ~]# ceph nvme-gw disaster-clear pool01 group01 DC3
```

Copy to clipboard

The location becomes eligible for failover, and workloads can return to that site.

### Managing namespace placement

Change the location of a namespace in an NVMe-oF stretch cluster to control data placement across sites.

#### About this task

Namespace location determines the preferred gateway site for I/O operations and is used by the load-balancing algorithm.

#### Procedure

Change the namespace location.

```plaintext-ibm
ceph nvmeof namespace update --nqn NQN --nsid NSID --location LOCATION
```

Copy to clipboard

> 📝 **Note:** Note:

- The specified location must exist on a gateway in the group.
- Invalid location assignments are rejected.

For example,

```
[root@host01 ~]# ceph nvmeof namespace update --nqn nqn.2016-06.io.spdk:cnode1.group1 --nsid ns1 --location DC2
```

The namespace is reassigned to a new preferred location.

#### What to do next

Verify that the namespace is served by a gateway in the expected location.

1. List namespace information by using the NVMe‑oF CLI.
2. Identify the gateway servicing the namespace.
3. Confirm that the gateway location matches the namespace location.

For example,

```plaintext-ibm
ceph nvmeof namespace list --nqn NQN

ceph nvme-gw listeners POOL_NAME GROUP_NAME
```

Copy to clipboard

> 📝 **Note:** Note:
Namespace placement is optimized based on location. If a matching gateway location is not available, the system assigns the namespace to another available gateway.
