## Bug fixes

Last Updated
: 2026-09-09

This section describes bugs with significant user impact, which were fixed in this release of IBM Storage Ceph. In addition, the section includes descriptions of fixed known issues found in previous versions.

SigV4 request validation is now enforced for Ceph Object Gateway

Previously, Ceph Object Gateway accepted SigV4 requests even when the `host` and `x-amz-*` headers were not included in the signed header set. This behavior was addressed as part of the fix for CVE-2026-54330. However, the multisite REST client generated requests with these improperly signed headers.

With this fix, Ceph Object Gateway rejects SigV4 requests that do not include the required `host` and `x-amz-*` headers in the signed header set. As a result, SigV4 request validation complies with security requirements.

> 📝 **Note:** Important:
For multisite deployments, set
`rgw_sigv4_insecure`
to
`true`
and use the
`--force`
option before starting the upgrade. After all clusters have been upgraded, set
`rgw_sigv4_insecure`
back to
`false`
on all clusters.

(IBMCEPH-15856)

### cephadm utility

Monitor configuration updates are now applied when the monitor daemon is restarted

Previously, monitor daemon configurations were not dynamically refreshed during a restart. As a result, updated settings such as public_network did not take effect, and the monitor continued to run with the previous configuration.

With this fix, monitor configuration updates are correctly applied when the monitor daemon is restarted. As a result, updated configuration values take effect without requiring manual redeployment.

(IBMCEPH-15002)

Host management and service placement now work correctly with uppercase hostnames after upgrade

Previously, hostname normalization changes converted hostnames to lowercase during upgrade. In clusters that were originally deployed with uppercase hostnames, existing cache dictionaries remained keyed with the original uppercase values, causing hostname lookups to fail.

With this fix, hostname normalization is handled correctly for clusters that contain uppercase hostnames created before the upgrade. As a result, host management operations and service placement work as expected after upgrade, and errors such as Failed to apply <n> service(s) and host <hostname> does not exist no longer occur.

(IBMCEPH-16538)

`mgmt-gateway`
services remain stable when using
`cephadm`
-signed certificates

Previously, when the `mgmt-gateway` service was configured with `certificate_source: cephadm-signed`, `cephadm` did not include the service specification when calculating persisted dependencies. As a result, the persisted and recalculated dependency lists did not match, causing cephadm to repeatedly reconfigure and redeploy the `mgmt-gateway` service. This behavior could cause the service to become unavailable.

With this fix, `cephadm` correctly includes the service specification when calculating and persisting dependencies for `mgmt-gateway`. The same correction also applies to `oauth2-proxy`. As a result, dependency lists remain consistent when `certificate_source: cephadm-signed` is configured, reducing unnecessary service reconfiguration and helping `mgmt-gateway` remain stable after deployment.

(IBMCEPH-17209)

External TLS certificates remain compatible across upgrades

Previously, cephadm could encounter issues when processing externally managed TLS certificate bundles that included intermediate certificates. In some cases, certificate validation could fail, and existing Ceph Object Gateway deployments that used legacy certificate settings could encounter issues after an upgrade.

With this fix, cephadm correctly processes complete TLS certificate bundles and supports migration of valid legacy Ceph Object Gateway certificate configurations. As a result, external TLS certificates are handled more reliably, and existing Ceph Object Gateway deployments remain compatible across upgrades.

(IBMCEPH-16113)

### Ceph Manager

Configuration commands now handle whitespace in section names correctly

Previously, `ceph config set`, `ceph config get`, and `ceph config rm` did not trim leading or trailing whitespace from the section name before parsing it. As a result, configuration values set for targets such as ` osd.0` or `osd.0 ` could be stored under an unintended key and fail to apply to the expected daemon.

With this fix, leading and trailing whitespace is removed from section names before they are parsed and matched. As a result, configuration commands correctly treat `osd.0`, ` osd.0`, `osd.0 `, ` osd.0 ` as the same target, ensuring that configuration values are applied, retrieved, and removed as expected.

(IBMCEPH-10858)

OSD redeployment now reuses available DB slots correctly

Previously, when redeploying an OSD with DB devices after a `ceph orch osd rm --zap --replace` operation, `ceph-volume` could incorrectly determine that no DB slots were available on an existing fast device volume group, even when a free slot was available. As a result, the OSD was not provisioned successfully and remained in a destroyed state.

With this fix, `ceph-volume` more accurately identifies available DB slots on existing fast device volume groups during OSD redeployment. Additional improvements were made to device allocation and drive selection logic to address related edge cases. As a result, OSD redeployment correctly reuses available DB slots on existing fast device volume groups, allowing the OSD to be provisioned successfully without manual intervention.

(IBMCEPH-15155)

### Ceph Dashboard

Dashboard Export Multi-site Realm Token feature now works correctly on secondary sites

Previously, on secondary sites, attempts to fetch primary zone parameters returned ENOENT, causing the `/api/rgw/realm/get_realm_tokens` API to return HTTP 500. As a result, the Dashboard Export Multi-site Realm Token feature failed for replicated realms, returning either an empty list or an internal server error.

With this fix, zone parameter retrieval on secondary sites falls back to locally available parameters when the primary zone is unavailable. As a result, the `/api/rgw/realm/get_realm_tokens` API correctly returns realm information and export tokens for replicated realms on both primary and secondary sites.

(IBMCEPH-16585)

Dashboard processing now handles malformed progress event references safely

Previously, the Ceph Dashboard could raise an exception when processing progress events because the `refs` field could contain unexpected or malformed data. As a result, the dashboard was unable to process progress events when `refs` was not in the expected format.

With this fix, validation was added for the `refs` field to safely handle dictionaries, valid key-value lists or tuples, `None`, and unexpected values. As a result, the dashboard can process progress events more reliably and avoids exceptions caused by malformed `refs` data.

(IBMCEPH-16427)

### Ceph File System (CephFS)

Retention field now validates time designators correctly

Previously, the `Retention` field accepted invalid duration values that did not include a valid time designator format. As a result, values such as 5Y were incorrectly accepted.

With this fix, strict validation is applied to the `Retention` field time designator. As a result, invalid values such as 5Y are rejected, and only correctly formatted retention durations are accepted.

(IBMCEPH-13004)

### Ceph Block Device mirroring

Ceph Block Device mirror snapshots are no longer pruned after image failover

Previously, after a Ceph Block Device image failover, obsolete primary and primary-demoted mirror snapshots were not removed until a subsequent promote or demote operation. As a result, unnecessary mirror snapshots accumulated on the secondary cluster and consumed additional storage, with the greatest impact on large images.

With this fix, the `rbd-mirror` daemon proactively removes obsolete primary and primary-demoted mirror snapshots immediately after a successful image failover. As a result, obsolete mirror snapshots are reclaimed sooner, reducing unnecessary storage usage on the secondary cluster.

(IBMCEPH-16990)

Mirror group snapshot scheduler is now FIPS compliant

Previously, the mirror group snapshot scheduler used MD5 hashing to calculate deterministic schedule phase offsets. Although the hash was not used for security purposes, MD5 operations were blocked in FIPS mode.

With this fix, the MD5 hash used for phase offset calculation is explicitly marked as not being used for security.As a result, the mirror group snapshot scheduler operates correctly in FIPS-enabled environments and is FIPS compliant.

(IBMCEPH-17724)

### Ceph Object Gateway

Topic queue reservation leak no longer causes false
ENOSPC
errors

Previously, the urgent_data.reserved_size field accumulated incorrect values over time due to a mismatch between the size added during `reserve()` and the size subtracted during `commit()` and `abort()`. As a result, urgent_data.reserved_size grew unbounded, eventually reaching the queue capacity limit and returning ENOSPC errors even when the queue had sufficient available space.

With this fix, reservation calculations are corrected so that the reservation value no longer leaks. In addition, a one-time self-healing mechanism recalculates and corrects the reservation counter on existing topic queues. As a result, topic queues return ENOSPC errors only when they reach their actual capacity limit, and existing queues with accumulated reservation leaks are automatically corrected.

(IBMCEPH-17438)

Ceph Object Gateway stability is improved during lifecycle and garbage collection processing

Previously, a race condition in asynchronous OMAP read processing could cause Ceph Object Gateway daemons to terminate unexpectedly under heavy workloads. Repeated daemon crashes could interrupt Lifecycle (LC) and Garbage Collection (GC) operations, leading to delayed cleanup and growth of the garbage collection queue.

With this fix, asynchronous worker task handling is coordinated correctly to ensure operations complete safely before resources are released. As a result, Ceph Object Gateway remains stable during concurrent OMAP read operations, allowing LC and GC processing to continue without interruption and preventing garbage collection queue buildup.

(IBMCEPH-17569)

### Multi-site Ceph Object Gateway

Empty shard trimming no longer loops indefinitely

Previously, a misplaced exception handler inside a loop could cause trimming operations on an empty shard to enter an infinite loop.

With this fix, the exception handling logic is moved outside the loop. As a result, trimming an empty shard completes correctly and no longer loops indefinitely.

(IBMCEPH-15576)

### Ceph NVMe-oF gateway

Correct hostname now displayed for NVMe-oF auto-listener list output

Previously, when you ran the ceph nvmeof listener list command, the Host column displayed the gateway daemon ID instead of the hostname for auto-listeners. This occurred because the command called nvme-gw listeners to retrieve auto-listener information, which returns the gateway daemon ID (`gw_id`) instead of the hostname. A reverse DNS lookup was used as a fallback, but DNS resolution failures caused the daemon ID to be displayed.

With this fix, NVMe-oF gateways call service dump at initialization to build a reliable gw_id-to-hostname map. If that lookup fails, a reverse DNS lookup is attempted. If DNS resolution also fails, the IP address is shown as a fallback. As a result, the Host column in ceph nvmeof listener list output now consistently displays the correct hostname for all auto-listeners.

(IBMCEPH-16391)

Auto-listeners now ignore interfaces in a
DOWN
state

Previously, if a network interface was in a DOWN state but still had an IP address within the configured network-mask subnet, the auto-listener attempted to create a listener on that address during redeployment. Because the interface was not active, listener creation failed and could cause the gateway to fail to start.

With this fix, auto-listeners no longer attempt to bind to addresses on interfaces that are in a DOWN state. As a result, gateway redeployment completes successfully, and the gateway starts correctly even when inactive interfaces retain IP addresses.

(IBMCEPH-14286)

NVMe-oF CLI now validates server addresses before returning results

Previously, the `ceph nvmeof` CLI did not validate values provided for the --server_address parameter. As a result, commands such as ceph nvmeof listener list returned results regardless of the address specified, making it difficult to determine which gateway was being queried.

With this fix, the NVMe-oF CLI validates --server_address values against known gateway addresses before returning results. As a result, the CLI returns an EINVAL error when an invalid or non-existent server address is specified and returns listener information only for a valid matching gateway.

(IBMCEPH-14187)

Listeners are no longer removed when a broader network mask still applies

Previously, removing a network mask from an NVMe-oF subsystem could cause listeners to be removed unexpectedly, even when another configured network mask still covered the listener IP addresses. As a result, valid listeners could disappear and the `ceph nvmeof listener list` command could return no listeners.

With this fix, listener evaluation correctly accounts for all remaining network masks before removing listener entries.As a result, listeners remain available when they are still covered by a configured network mask, preventing unintended connectivity issues.

(IBMCEPH-14023)

### RADOS

Crash daemon now retains correct access to the crash directory after service deployments

Previously, deploying certain services such as Grafana changed the permissions of the crash directory path, preventing the crash daemon from accessing the directory and functioning correctly.

With this fix, the crash directory permissions are correctly preserved when services are deployed. As a result, the crash daemon retains access to the crash directory path without requiring manual intervention after each deployment.

(IBMCEPH-14999)

Ceph Monitors remain stable during multiple monitor removals

Previously, when multiple monitors were removed from the monmap in a single update, the monitor rank adjustment logic could fail to maintain consistency between the local rank and the recalculated rank in the monmap. This issue could trigger an assertion failure and cause a Ceph Monitor to crash.

With this fix, the monitor uses the recalculated rank provided by the monmap instead of attempting to adjust the rank iteratively during monitor removal processing. As a result, Ceph Monitors can process updates that remove multiple monitors in a single monmap update without triggering this assertion failure.

(IBMCEPH-15723)

### NFS service

CIDR prefix length
`/0`
is now accepted in NFS share client blocks

Previously, the CIDR suffix lexer rejected a prefix length of `0` because the regex pattern required the first digit to be in the range `1`–`9`. As a result, valid CIDR notations such as `0.0.0.0/0` (RFC 4632) and `::/0` (RFC 4291) could not be used in NFS share client blocks to match all addresses in an address family.

With this fix, the regex accepts a prefix length of `/0` while still disallowing leading zeros in other positions. As a result, `0.0.0.0/0` and `::/0` are now valid in NFS share client block definitions.

(IBMCEPH-15732)

NFS server metrics are now exposed by default

Previously, NFS server metrics were not exposed through the HTTP metrics endpoint because metrics collection was not enabled in the ganesha.conf configuration.

With this fix, the `Enable_Metrics` setting is enabled in ganesha.conf file. As a result, NFS metrics are exposed by default through the HTTP metrics endpoint on port 9587 (`http://LOCAL_IP:9587`).

(IBMCEPH-17615)

NFS service upgrades now complete without QoS type compatibility errors

Previously, upgrades could fail because the qos_type parameter changed from an integer value to a string value in a previous release. As a result, the NFS service daemon could crash when processing the parameter during an upgrade.

With this fix, the NFS service accepts both integer and string values for qos_type. As a result, NFS service upgrades complete successfully without daemon crashes caused by qos_type compatibility issues.

(IBMCEPH-16314)

### SMB file services

SID-to-name resolution restored for Active Directory joined SMB deployments

Previously, the host-side /run directory bind-mounted into SMB containers was created with permissions `0770`, blocking access for non-owner processes. As a result, communication between smbd and winbindd over Unix domain sockets failed, causing SID-to-name resolution failures in Active Directory joined deployments.

With this fix, the permissions of the bind-mounted /run directory are changed from `0770` to `0755` to match standard /run semantics. As a result, smbd and winbindd communicate correctly, and SID-to-name resolution works as expected in Active Directory joined SMB deployments.

(IBMCEPH-15780)

SMB cluster-wide IO rate limiting is now enforced when multiple SMB shares are configured

Previously, the `ratelimitd` daemon aggregated active smbd process counts across all SMB shares and broadcast a single global total. Each share's rate limiter then divided its configured limit by this inflated count instead of the count for its own share. As a result, in deployments with multiple `aio_ratelimit-enabled` shares, the enforced per-process limit was lower than intended. For example, with 2 shares each configured with a 1000 IOPS limit and 5 active processes each, each process computed 1000/10 instead of 1000/5, effectively halving the allowed throughput.

With this fix, the `ratelimitd` daemon groups process activity reports by share name and broadcasts a separate node summary per share. As a result, each share's rate limit is divided only among the processes actively serving that share, correctly enforcing the configured limit.

(IBMCEPH-16198)
