## CephX daemon keyrings

Last Updated
: 2026-09-06

A daemon keyring stores a secret key and capabilities for a specific Ceph daemon. CephX uses these keyrings to authenticate each daemon with the Monitor before the daemon can participate in the cluster.

When a Ceph daemon starts, it reads its keyring file and presents its credentials to the Monitor. The Monitor verifies the key and issues a time-limited session ticket that the daemon uses for all subsequent cluster communication. Each daemon has its own unique keyring containing a secret key and a set of capabilities that define what the daemon is authorized to do.

Administrative users or deployment tools such as `cephadm` generate daemon keyrings in the same way as generating user keyrings. By default, Ceph stores daemon keyrings inside the daemon data directory.

> 📝 **Note:** Important:
The Monitor keyring contains a key but no capabilities, and is not part of the cluster
`auth`
database. Monitor keyrings are used only during initial cluster bootstrap for peer-to-peer Monitor authentication.

### Daemon keyrings and client keyrings

Both daemon keyrings and client keyrings use the CephX protocol, but they serve different purposes and are managed differently.

| Attribute | Daemon keyrings | Client keyrings |
| --- | --- | --- |
| Entity name format | TYPE.ID — for example, osd.0, mgr.node1, mds.cephfs1 | client.NAME — for example, client.admin, client.rgw |
| Purpose | Authenticate a running cluster daemon with the Monitor | Grant a user, application, or service access to cluster data |
| Capabilities | Scoped to the minimum permissions required for that daemon type | Defined by the administrator based on access requirements |
| Default storage location | /var/lib/ceph/FSID/DAEMON-NAME/keyring (cephadm deployments) | /etc/ceph/ceph.client.admin.keyring or application-specific path |
| Management | Created and rotated automatically by cephadm | Created and managed by the cluster administrator |

### Default keyring locations

In deployments that use the `cephadm` orchestrator, the daemon data directory defaults to the following path on the host where the daemon runs:

```plaintext-ibm
/var/lib/ceph/FSID/DAEMON-TYPE.DAEMON-ID/keyring
```

> 📝 **Note:** CAUTION:
The
`cephadm`
orchestrator bind-mounts each daemon keyring into the daemon container at
`/etc/ceph/keyring`
. Do not manually copy or modify keyring files managed by
`cephadm`
. Manual changes may conflict with the credentials stored in the Monitor authentication database and cause authentication failures.

### Anatomy of a daemon keyring file

A keyring file is a plain-text file in INI format. Each section corresponds to a CephX entity. The following example shows the keyring for `osd.0`:

```plaintext-ibm
[osd.0]
        key = AQCvCKRkAAAAABAAX1mxBEDDMnHkubu0hJPk2A==
        caps mgr = "allow profile osd"
        caps mon = "allow profile osd"
        caps osd = "allow *"
```

Copy to clipboard

`[osd.0]`
The entity header in the format
`DAEMON-TYPE.DAEMON-ID`
. This value must match the CephX entity registered in the Monitor authentication database.
`key`
The Base64-encoded secret key used to generate and verify CephX authentication tickets. Treat this value as a sensitive credential and restrict read access to the keyring file.
`caps`
Capabilities that define what operations this entity is authorized to perform against each daemon type. The
`allow profile osd`
shorthand grants the standard permissions required for an OSD to function. The
`allow *`
on the
`osd`
capability grants the OSD full access to peer OSDs, which is required for replication and recovery operations.

### Capabilities by daemon type

The following table summarizes the standard capability profiles that `cephadm` assigns when it creates a daemon keyring. The `allow profile TYPE` shorthand is a built-in CephX profile that expands to the exact capability set required for that daemon type.

| Daemon type | Default capabilities |
| --- | --- |
| Monitor (mon.ID) | caps mon = "allow *"Copy to clipboard Monitors require full access to the cluster map and authentication database. The Monitor keyring is used only during bootstrap and contains no capabilities in the cluster auth database. |
| OSD (osd.ID) | caps mgr = "allow profile osd" caps mon = "allow profile osd" caps osd = "allow *"Copy to clipboard OSDs report status to the Manager and Monitor, and communicate with peer OSDs for replication and recovery. |
| Manager (mgr.ID) | caps mds = "allow *" caps mon = "allow profile mgr" caps osd = "allow *"Copy to clipboard The Manager aggregates cluster-wide metrics and runs orchestration and monitoring modules, requiring broad read and write access. |
| MDS (mds.ID) | caps mds = "allow" caps mon = "allow profile mds" caps osd = "allow rwx pool=CEPHFS-POOLS"Copy to clipboard Each MDS instance requires access to the CephFS metadata and data pools. |

### Keyring lifecycle in cephadm deployments

`cephadm` manages the keyring lifecycle automatically.

Creation
When
`cephadm`
deploys a daemon, it calls
`ceph auth get-or-create`
to register a CephX entity in the Monitor authentication database and writes the returned keyring to the host storage path.
Startup authentication
When the daemon container starts, it reads the keyring and presents its credentials to the Monitor. The Monitor verifies the key and issues a time-limited session ticket used for all subsequent cluster communication.
Key rotation

To rotate a daemon key without redeploying the daemon, run:

```plaintext-ibm
ceph orch daemon rotate-key DAEMON-TYPE.DAEMON-ID
```

Copy to clipboard

`cephadm` generates a new key, updates the Monitor authentication database, and rewrites the keyring file on the host.

Daemon removal
When you remove a daemon with
`ceph orch daemon rm`
,
`cephadm`
removes the CephX entity from the Monitor authentication database and deletes the keyring from host storage.

### Inspecting daemon keyrings

Use the following commands to inspect and verify daemon keyring configuration.

List all authentication entities in the cluster

```plaintext-ibm
ceph auth ls
```

Display the keyring for a specific entity

```plaintext-ibm

```
