## Configure multi-active NFS gateway

Last Updated
: 2026-06-25

Configure an multi-active NFS deployment by using NFS behind an ingress service (HAProxy and Keepalived).

### Before you begin

Before you begin, make sure that you have the following prerequisites in place:

- Ensure that the Ceph cluster is deployed and accessible.
- Ensure that CephFS or Ceph Object Gateway backend services are configured.
- Identify the hosts for NFS daemons and ingress services.
- Ensure that all the manager, monitor, and OSD daemons are deployed.
- Ensure that the number of hosts is greater than the placement count for the NFS service.
- Ensure that the NFS module is enabled.

### About this task

In the multi-active architecture:

- Multiple NFS daemons serve the same set of shares backed by CephFS or Ceph Object Gateway.
- HAProxy distributes client traffic across these NFS servers.
- Keepalived manages a virtual IP (VIP) to provide a single service endpoint.

To maintain session consistency, it relies on haproxy stick tables to preserve client-to-server affinity. This ensures that a given client continues to communicate with the same NFS instance.

NFS maintains client state, such as locks, sessions, and delegations, on the server.

> 📝 **Note:** Note:
If a client is redirected to a different backend:

- The new NFS server cannot reclaim or recognize the client’s state.
- This can result in hung I/O, stale locks, or session recovery failures.

### Procedure

1. Log in to the
`cephadm`
shell.

```plaintext-ibm
[root@host01 ~] cephadm shell
```

Copy to clipboard
2. Create an NFS specification file.

```plaintext-ibm
vi nfs.yaml
```

Copy to clipboard
3. Define the NFS service configuration with placement count.

```plaintext-ibm
service_type: nfs
service_id: NFS_SERVICE_ID
placement:
  count: PLACEMENT_COUNT
  hosts:
    - HOST1
    - HOST2
    - HOST3
spec:
  enable_haproxy_protocol: true|false
  port: NFS_PORT
colocation_ports:
      data_port: DATA_PORT
      monitoring_port: MONITORING_PORT
      cluster_qos_port: CLUSTER_QOS_PORT
```

Copy to clipboard

`service_type`
Specifies the service type. Set this value to
`nfs`
.
`service_id`
Specifies a unique identifier for the NFS service.
`placement.hosts`
Specifies the hosts on which the NFS daemons run.
spec.colocation_ports
Specifies the ports required by the NFS daemons when multiple daemons are colocated on the same host.
**data_port:**
Port used for data traffic
**monitoring_port:**
Port used for monitoring
**cluster_qos_port:**
Port used for cluster QoS
For example,

```
service_type: nfs
service_id: nfs-cluster

placement:
  count: 2
  hosts:
    - node1
    - node2
    - node3
spec:
  enable_haproxy_protocol: true
  port: 12049
colocation_ports:
      data_port: 3049
      monitoring_port: 9588
      cluster_qos_port: 31312
```

> 📝 **Note:** Note:

- The NFS service must be configured with a placement count to maintain client-server affinity.
- You can define the placement count based on deployment requirements.
- Ensure that the number of hosts exceeds the placement count.

  - You can define the placement count based on deployment requirements.
  - Ensure that the number of hosts exceeds the placement count.
4. Apply the specification.

```plaintext-ibm

```

Copy to clipboard

```
ceph orch apply -i nfs.yaml
```

5. Create an ingress specification file.

```plaintext-ibm
vi ingress.yaml
```

Copy to clipboard
6. Define the ingress configuration:

```plaintext-ibm
service_type: ingress
service_id: INGRESS_SERVICE_ID
placement:
  hosts:
    - HOST1
    - HOST2
spec:
  backend_service: nfs.nfs-cluster
  enable_haproxy_protocol: %true|false;
  first_virtual_router_id: VRRP_ROUTER_ID
  frontend_port: FRONTEND_PORT
  monitor_port: MONITOR_PORT
  virtual_ip: VIRTUAL_IP
  haproxy_peer_communication_port: HAPROXY_PEER_COMMUNICATION_PORT
  health_check_interval: INTERVAL
```

Copy to clipboard

service_type
Specifies the service type. Set this value to
`ingress`
.
service_id
Specifies a unique identifier for the ingress service.
placement.hosts
Specifies the hosts on which the ingress service (HAProxy and Keepalived) runs.
backend_service
Specifies the NFS service that the ingress service load-balances.
enable_haproxy_protocol
Enables HAProxy PROXY protocol support so that backend NFS daemons can receive the client IP address.
frontend_port
Specifies the port that is exposed to NFS clients. The default value is typically 2049.
monitor_port
Specifies the port used for HAProxy monitoring and statistics.
virtual_ip
Specifies the virtual IP address that is shared across ingress nodes and used by clients to access the service.
haproxy_peer_communication_port
Specifies the port used for HAProxy peer synchronization, including sharing stick-table information between ingress nodes.

> 📝 **Note:** Note:
The default value of health_check_interval is set to 30 seconds. However, you should adjust this value based on your cluster size, workload characteristics, and recovery requirements to ensure optimal performance and failover behavior.

> 📝 **Note:** Note:
Configure the
`health_check_interval`
value so that the total failure detection time (interval multiplied by three consecutive failures) is greater than the time required for an NFS daemon to start and become ready. If the detection time is too short, a recovering backend might be marked as unavailable, which can cause traffic re

- HAProxy stick-table information is not persistent across restarts. Avoid restarting or redeploying the ingress service (HAProxy and Keepalived) after clients begin accessing the service, as this can disrupt client-to-server affinity.
- NFS daemons can run in a colocated configuration to maintain the required number of backend servers. If an NFS daemon stops or enters an error state, it does not fail over automatically. Clients connected to that daemon can experience hung I/O operations. To recover, unmount and remount the affected client.

```
service_type: ingress
service_id: nfs-cluster
placement:
  hosts:
    - node1
    - node2
spec:
  backend_service: nfs.nfs-cluster
  enable_haproxy_protocol: true
  first_virtual_router_id: 50
  frontend_port: 2049
  monitor_port: 9049
  virtual_ip: 1.2.3.4
  haproxy_peer_communication_port: 1024
  health_check_interval: 5s
```
