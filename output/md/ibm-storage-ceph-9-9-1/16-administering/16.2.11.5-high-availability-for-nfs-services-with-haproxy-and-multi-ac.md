## High availability for NFS services with HAProxy and multi-active servers

Last Updated
: 2026-09-10

High availability Proxy (HAProxy) for Network File System (NFS) is a setup where HAProxy acts as a front-end load balancer for NFS server instances. This configuration enables seamless failover and session recovery while preserving the stateful nature of the NFS protocol.

NFS HAProxy is a proxy server that receives requests on a dedicated virtual IP (VIP). This proxy server operates over Transmission Control Protocol (TCP).

When HAProxy fronts NFS services in a Ceph cluster, clients mount the NFS file share using the VIP instead of the physical NFS server IP address. HAProxy receives client requests and forwards them to backend NFS servers based on the configured load balancing algorithm and current server load.

> 📝 **Note:** Note:

- HAProxy support is available only for NFS version 4 (NFSv4).
- Daemon failover is triggered only if the daemon is absent, either due to explicit removal or because the host is unavailable. A daemon that is present but reporting an error/stopped state does not trigger failover.

### Stateful protocol handling and failover

The following points describe how NFS handles stateful protocol operations and failover.

- NFS is a stateful protocol, so HAProxy must maintain state information for every connected NFS client.
- If an NFS server fails, Ceph attempts to recover the instance on the same node (if available) or on another node labeled for NFS service.
- Once the server restarts, HAProxy initiates client recovery using its internal state tracking.

> 📝 **Note:** Note:
I/O operations may be interrupted during server recovery, but clients do not receive I/O errors unless the server cannot restart.

### Health checks and recovery time

The following points describe how HAProxy performs health checks and manages recovery timing.

- The appropriate health_check_interval value depends on the number of nodes in the cluster.
- For a Ceph cluster with up to five nodes, the configuration process typically completes in approximately 2 minutes. For clusters with up to ten nodes, the process may take around 5 minutes.

> 📝 **Note:** Note:
Configuration time depends on the size and complexity of the Ceph cluster, as well as the system environment and network conditions.
- For smaller clusters, a value of approximately 2 minutes can be sufficient.

> 📝 **Note:** Note:
Validate this setting by testing NFS daemon failover scenarios before starting client I/O operations to ensure stable behavior.
- If this combined duration is shorter than the NFS daemon startup time, a recovering backend may be prematurely marked as down, leading to unnecessary traffic redistribution, loss of client affinity, and potential client hangs.
