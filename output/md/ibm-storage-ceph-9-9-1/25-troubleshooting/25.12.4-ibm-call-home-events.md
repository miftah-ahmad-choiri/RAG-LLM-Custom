## IBM Call Home events

Last Updated
: 2026-06-25

Hardware status and critical events get sent from IBM Storage Ceph to IBM Call Home, when IBM Call Home is enabled.

Hardware status events, also known as inventory events, are sent to IBM Call Home.

Table 1
lists the different hardware events that are sent out to
IBM
Call Home. For more details about any of the hardware errors, use the
ceph health detail
command on your storage cluster.

> 📝 **Note:** Note:
Hardware status events are only for applicable deployments.

| Alert | Description |
| --- | --- |
| HardwareStorageError | Some storage devices are in error. |
| HardwareMemoryError | One or more DIMM errors are detected. |
| HardwareProcessorError | One or more processor errors are detected. |
| HardwareNetworkError | One or more network errors are detected. |
| HardwarePowerError | One or more power supply errors are detected. |
| HardwareFanError | One or more fan errors are detected. |

### Critical events sent to IBM Call Home

Table 2 lists the different critical events that IBM Call Home receives.

| Alert | Description |
| --- | --- |
| CephHealthError | The cluster state has been with a HEALTH_ERROR for more than 5 minutes. For more information, use the ceph health detail command on your storage cluster. |
| CephMonDownQuorumAtRisk | There is less than the minimum number of monitors active. Without quorum, the cluster becomes inoperable, affecting all services and connected clients. This alert provides a list of which monitors are down and on which host. |
| CephMonDiskspaceCritical | The space available to a monitor's store is critically low. Increase the space available to the monitors. The default directory is /var/lib/ceph/mon-*/data/store.db on traditional deployments, and /var/lib/rook/mon-*/data/store.db on the mon pod's worker node for Rook. Search your directory for old, rotated versions of *.log and MANIFEST. Important: Do not change or delete any .sst files. Other common directories to look in include: /var/lib/rook and other directories on the same file system. /var/log /var/tmp This alert provides a list of your monitor hosts. |
| CephOSDDownHigh | This alert provides a list of OSDs that are down and where they are located. |
| CephOSDFull | An OSD has reached the FULL threshold. Writes to pools that share the affected OSD are blocked. Use the ceph health detail and ceph osd df commands to help with identifying the specific problem. To resolve, do one or more of the following: Add capacity to the affected OSD's failure domain Restore down or out OSDs Delete any unwanted data |
| CephDeviceFailurePredictionTooHigh | Devices predicted to fail by the device health module cannot be automatically fixed since too many OSDs would be removed from the cluster to maintain performance and availability. Prevent data integrity issues by adding new OSDs so that data can be relocated. |
| CephFilesystemDamaged | Ceph File System (CephFS) metadata has been corrupted. Data may be inaccessible. Analyze metrics from the MDS daemon admin socket, or escalate to support. |
| CephFilesystemOffline | All MDS ranks are unavailable. The MDS daemons managing metadata are down, rendering the file system offline. |
| CephFilesystemDegraded | One or more metadata daemons (MDS ranks) are failed or in a damaged state, leaving CephFS in either only a partially available or not usable condition. |
| CephFilesystemFailureNoStandby | An MDS daemon has failed, leaving only one active rank and no available standby. Investigate the cause of the failure or add a standby MDS. |
| CephFilesystemReadOnly | The file system changed to READ ONLY status, due to an unexpected error when writing to the metadata pool. Either analyze the output from the MDS daemon admin socket, or escalate to support. |
| CephMgrModuleCrash | One or more Ceph Manager modules have crashed and have yet to be acknowledged by an administrator. A crashed module may impact functionality within the cluster. Use the ceph crash command to determine which module has failed, and archive it to acknowledge the failure. |
| CephMgrPrometheusModuleInactive | The module has either been disabled or the manager daemon is down. Without the working module, metrics and alerts will no longer function. To resolve, open a shell to an admin node or toolbox pod and use the ceph -s command to determine whether the manager is active. If the manager is not active, restart it. If the manager is active, determine the module status with the ceph mgr module ls command. If it is not listed as enabled, enable it with the ceph mgr module enable Prometheus command. |
| CephPGsInactive | This alert lists how many placement groups (PGs) have are inactive for more than 5 minutes in a pool. Inactive placement groups are not able to serve read/write requests. |
| CephPGsDamaged | During data consistency checks (scrub), at least one placement group (PG) has been flagged as being damaged or inconsistent. Check to see which PG is affected, and attempt a manual repair if necessary. To list problematic placement groups, use the rados list-inconsistent-pg POOL command. To repair PGs, use the ceph pg repair PG_NUM command. |
| CephPGRecoveryAtRisk | Data redundancy is at risk since one or more OSDs have reached or are higher than the FULL threshold. Add more capacity to the cluster, restore down or out OSDs, or delete unwanted data. |
| CephPGUnavailableBlockingIO | Data availability is reduced, impacting the cluster's ability to service I/O. One or more placement groups (PGs) are in a state that blocks I/O. |
| CephPGBackfillAtRisk | Data redundancy may be at risk due to lack of available space within the cluster. One or more OSDs have reached the BACKFILLFULL threshold. To resolve, add more capacity, or delete unwanted data. |
| CephNodeRootFilesystemFull | This alert gives what percentage of the root volume is available. |
| CephPoolFull | A pool has reached its maximum quota, or OSDs supporting the pool have reached the FULL threshold. Until this error is resolved, writes to the pool are blocked. To resolve, do one of the following: Increase the pool's quota First add capacity to the cluster and then increase the pool's quota. Use the ceph osd pool set quota POOL_NAME max_bytes BYTES command. |
| CephadmUpgradeFailed | The cephadm cluster upgrade process has failed. The cluster remains in an undetermined state. To understand the issue, review the cephadm logs. For more information, see cephadm troubleshooting. |
| CephadmDaemonFailed | A daemon that is managed by cephadm is no longer active. Determine, which daemon is down by using the ceph health detail command. Start a daemon by using the ceph orch daemon start DAEMON_ID command. |
| HardwareStorageError | Some storage devices have errors. For more information, use the ceph health detail command. |
| HardwareMemoryError | One or more DIMM errors are detected. For more information, use the ceph health detail command. |
| HardwareProcessorError | One or more processor errors are detected. For more information, use the ceph health detail command. |
| HardwareNetworkError | One or more network errors are detected. For more information, use the ceph health detail command. |
| HardwarePowerError | One or more Power supply errors are detected. For more information, use the ceph health detail command. |
| HardwareFanError | One or more fan errors are detected. For more information, use the ceph health detail command. |
| PrometheusJobMissing | The Prometheus job that scrapes from Ceph is no longer defined. As a result, you will not get metrics or alerts for the cluster. Review the job definitions in the prometheus.yml file of the Prometheus instance. |
| CephObjectMissing | The latest version of a RADOS object cannot be found, although all OSDs are up. I/O requests for this object from clients will be blocked (hang). Resolving this issue may require the object to be rolled back to a prior version manually, and manually verified. |
| CephDaemonCrash | One or more daemons have crashed recently, and need to be acknowledged. This notification ensures that software crashes do not go unseen. To acknowledge a crash, use the ceph crash archive ID command. |
| CephRBDMirrorImagesPerDaemonHigh | There are more than the 100 image replications per daemon. This is above the 100 image replication threshold. |
| CephRBDMirrorImagesNotInSync | There are Ceph Block Devices that are not in sync. Both local and remote Ceph Block Device (rbd) mirror images must be synced. |
| CephRBDMirrorImagesNotInSyncVeryHigh | More than 10% of the images have synchronization problems. |
